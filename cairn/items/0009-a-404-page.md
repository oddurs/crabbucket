## Problem

GitHub Pages serves `404.html` from the site root for any unmatched path. A
site without one gets GitHub's generic page, which is a jarring exit from a
site that otherwise looks like something.

The client router also needs it: a fetch that 404s currently falls back to a
full page load, which then lands on that same generic page.

## Proposal

`content/404.md` renders to `dist/404.html` — a file, not a directory, since
that is what Pages looks for. It is excluded from the route set, from the
navigation, and from link checking as a *target* (nothing should link to it),
but its own outgoing links are still checked.

Scaffold one in `crab new`.

Note the interaction with `base`: on a project site the 404 is served for
paths under `/repo/`, and relative links from it resolve against wherever the
user actually was. Use absolute `Url::new` links in the 404 layout for that
reason, and write down why.

## Acceptance criteria

- [x] `content/404.md` becomes `dist/404.html`
- [x] The 404 route is not in the site index or navigation
- [x] Links *from* the 404 page are checked; links *to* it are not required
- [x] The 404 layout uses absolute URLs, with a comment saying why
- [x] `crab new` scaffolds one

## 2026-09-08

Done. 404 is a page but not a route: partitioned out before the SiteIndex is built, written as 404.html rather than a directory, excluded from nav and from the route table. It is checked as though it sat at the site root, and any relative link on it fails the build with Reason::RelativeOnErrorPage -- the error page is served in place of every missing path, so a relative link there has no directory to resolve against. Found a real bug doing this: a bare #fragment was being looked up through the route table, so the 404's own heading permalinks were checked against the root page. Bare fragments now check against the page's own anchors, which is correct for every page and not only this one.
